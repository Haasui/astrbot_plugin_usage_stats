## A. 补丁到底装上没有

> 上机看 A1 / A3 / A4（§1.1、§1.2）；A2 的规则已由 `test_collect_covers_base_and_overrides_only` 覆盖。

| # | 验什么 | 怎么验 | 预期 | 验不过说明 |
| ---: | :--- | :--- | :--- | :--- |
| A1 ✓ | 装上了几处 | 开 `enabled` 后看启动日志的 `装了 N 处补丁` | N ≥ 2，且列表里出现具体**子类**名（如 `OpenAISource.text_chat`） | 如果只有 `Provider.text_chat`，说明子类枚举没生效——**整个方案失效** |
| A2 | 基类桩没被当成唯一目标 | 看 A1 的列表 | 除基类外至少还有一个子类 | 只剩基类 = 一个调用都记不到 |
| A3 | **初始化时挂不上、之后补得上** | 看重扫日志 | 默认每 60 秒重扫一次。若 A1 显示的处数一开始偏少，过一分钟会打出「补挂 N 处补丁」 | |
| A4 | 重扫不重复挂 | 挂上后等几轮重扫 | 处数不变（`install` 靠函数上的 MARK 幂等），不会有「补挂」日志刷屏 | |

A1 是全清单最重要的一条。`provider.py:100` 的基类方法体是 `...`，子类覆写会遮蔽它。

**A3 的原因是**：AstrBot 的 provider 子类是**按需导入**的（`dynamic_import_provider`）。
插件初始化跑在它们被导入之前时，`Provider.__subclasses__()` 是空的——一处都挂不上，
而且因为没有调用，也没有任何事件能触发重扫。所以重扫是时间驱动的。

**B5 的症状很显眼**：第一版里每一次调用都被记到本插件头上，排行里只有一行、占比 100%。
根因是补丁的包装函数活在 `data.plugins.astrbot_plugin_usage_stats.patch` 里，是栈上最内层的
`data.plugins.*`。若再看到这个形状，就是 `plugin_from_modules(..., ignore=...)` 没传进去。

**B4 是隐性依赖**：归因靠 `data.plugins.` 这个前缀，它是 AstrBot 的内部约定，不是公开 API。
升级本体时第一个要复查的就是它。

## C. 数据对不对

> 上机看 C1 / C3~C8（§1.2）；C2 已有截图作证（§0）。

| # | 验什么 | 怎么验 | 预期 |
| ---: | :--- | :--- | :--- |
| C1 | 用量字段搬对了 | 找一条记录，对比 provider 原始 `usage` | `input_other / input_cached / output` 三个数一致，`total` 相等 |
| C2 ✓ | 缓存命中有值 | 连续发同一条消息（DeepSeek 系有缓存） | `input_cached` 从 0 变成非 0 |
| C3 | 失败也记 | 故意配一个错的 provider，发一条 | `calls` 加 1、`failed` 加 1 |
| C4 | 图片张数 | 发一条带 3 张图的消息 | `images = 3`。这一列是**真正传给 provider 的**图片数（`image_urls` kwarg，见 `provider.py:104`）；provider 不支持图片时 runner 会传空列表（`tool_loop_agent_runner.py:354`），那时是 0 而不是 3 |
| C5 | 主对话的会话 | 开 `debug`，看日志行里的 `会话=` | 形如 `aiocqhttp:group:123456`，不是 `no_session` |
| C6 | **插件调用的会话**（最容易失败的一条） | 触发插件调模型，看那行的 `会话=` | 该笔调用落在**正确的会话**下，不是 `no_session` |
| C7 | 后台任务里的调用 | 触发一个定时/主动任务去调模型 | `no_session` 是预期结果，不是缺陷 |
| C8 | 缓存命中的空分母 | 找一个只有输出、没有输入的模型 | 插件行和模型行都显示「—」，不是 `0%`。`0%` 是「测过没命中」的意思 |
| C9 | 流式回复的命中率 | 发一条会走流式、且供应商有缓存的普通对话，看视图 | 「缓存命中」是百分比。显示「—」而右边「缓存」列有数字，就是这一版修的问题又回来了 |

**C6 是这一组的关键**：它验证「从调用栈捞 event」这条路径成立。捞不到的话，
只有主对话带会话，插件那部分用量就归不到任何会话上。

## D. 越界的副作用（风险最高的一组）

> **这一组风险最高**，D1~D7 都在 §1.2。D2 是越界唯一的退路。

| # | 验什么 | 怎么验 | 预期 | 验不过怎么办 |
| ---: | :--- | :--- | :--- | :--- |
| D1 | super() 不双记 | 找一个会 `super().text_chat()` 的 provider 类型，发一条 | 记录数 = 实际调用数；`跳过重入` 计数增加 | 看 `跳过重入` 是否为 0——**是 0 且记录翻倍，说明 `_DEPTH` 没起作用** |
| D2 | 卸载精确还原 | 关掉插件，看 `还原 N 处补丁` | N == A1 里装上的数量 | 少了 = 有补丁泄漏 |
| D3 | 热重载不叠加 | 连续重载插件 3 次 | `/usage` 的记录数不翻倍 | 翻了 = `MARK` 幂等没生效 |
| D4 | 流式没被弄坏 | 触发一次流式回答 | 流式输出正常，且**有** `text_chat_stream` 的记录。**流中途断了要记成一次失败**（`failed` 加 1），不是拿最后一片当成功 | 流式坏了 = 异步生成器分支写错了（这是最脆的一处） |
| D5 | 记账失败不伤对话 | 临时在 `_record` 里 `raise`，发一条 | 对话正常回，`记账失败` 计数增加 | 对话挂了 = try/except 没包全 |
| D7 | 非异步的 provider 方法 | 配一个 `text_chat` 写成普通 `def` 的 provider（少见，第三方 provider 插件可能有） | 调用照常返回，**不被记账搞挂**；记录里 response 就是它的返回值 | 报 TypeError = 包装器对非协程方法也会去 `await` |
| D6 | 与 token_controller 共存 | 两个都开着 | 不报错；`token_controller` 的限额仍然生效 | 它的 `main.py:829/:1126` 也碰 provider 对象，需实测 |

**D4 和 D1 是这套补丁的两个已知脆弱点**，逐条盯。D2 是越界唯一的退路。
