# 用量统计调用日志读取与状态设计

> 调用日志有界尾读的设计记录。现行接口与统计行为见 [使用说明](<../README.md>) 和 [架构说明](<ARCHITECTURE.md>)。

本提案为调用日志增加有界尾读和明确的 UI 状态，避免读取错误与“尚无记录”混为一谈。

## 1. 摘要

建议把调用日志 API 的全文件读取改为有界尾读，并让视图区分未启用、空日志、读取失败、部分结果和成功。第一阶段上限建议为 **5000 行或 8 MiB**，先到上限者生效；日志面板明确提示结果可能截断。读取始终发生在用户打开或刷新日志标签页时，不加入自动轮询。

该改动只影响可选调用日志，不改变用量统计结果、provider 请求或响应。日志包含会话标识，页面和导出操作应明确提示这一点。

## 3. 目标与非目标

### 3.1 目标

- 限制一次日志读取的最大内存和响应体积。
- 对没有记录、功能关闭和文件不可读提供不同反馈。
- 不因数据过旧或较新请求较慢而覆盖当前选择。
- 让维护者知道截断边界，并在查看或导出前看到会话标识提示。

### 3.2 非目标

- 不改 usage.json 的格式、聚合结果或保留天数。
- 不提供服务端分页、任意偏移读取或无限量导出。
- 不把调用日志变成默认开启，也不保存请求正文。
- 不显示服务器绝对路径。
- 不引入第三方日志或图表依赖。

## 4. 定义

- **行上限**：单次响应最多返回的完整日志行数，建议 5000。
- **字节上限**：单次读取最多扫描并解码的日志字节数，建议 8 MiB。
- **截断**：文件中仍有更旧的行，但本次因行或字节上限未返回。
- **空日志**：调用日志已启用、数据路径可用，且当前持久化文件没有可返回的完整记录。
- **读取失败**：数据路径不可用，或文件打开、读取失败。文件尚未创建但路径可用不属于读取失败。

## 5. 功能设计

### 5.1 有界尾读

在 main.py 的调用日志读取路径中调用独立标准库模块 log_tail.py。建议 helper 接受二进制 file-like 对象、最大行数和最大读取字节数，返回完整行、截断标记与实际扫描字节数。helper 从文件末尾以固定大小二进制块向前扫描，直到收集足够行或达到字节上限；只解码选中的完整行，使用 UTF-8 errors=replace 与当前行为保持一致。

建议常量：MAX_CALL_LOG_TAIL_LINES = 5000，MAX_CALL_LOG_READ_BYTES = 8 * 1024 * 1024。UI 的“全部”改为“最多 5000 条”，并在字节上限先到时显示截断提示。导出内容与当前选定尾部一致，不额外读取完整文件。

边界规则：

- 文件末尾有换行时，不把终止换行误算成空记录。
- 最后一条没有换行时仍纳入结果。
- 如果字节上限落在一条记录中间，丢弃不完整的首行，不输出破损记录，并标记 truncated。
- 一条日志本身超过字节上限时，不返回其半条文本，响应标记 truncated，并提示该行无法完整显示。
- 每次响应只保留最多 5000 条完整行，并报告实际返回的行数。

### 5.2 查询与响应

保持 GET /astrbot_plugin_usage_stats/stats 现有主统计行为。未提供 tail 或 tail=0 仍返回统计摘要。有效 tail 请求进入日志分支。超过上限的正整数按最大值截断；无法解析或为负数的 tail 返回可识别的 invalid_request 状态，不得误走统计摘要分支。

日志响应建议保留 enabled、path、lines 三个现有键，新增状态字段：

~~~json
{
  "enabled": true,
  "path": "现有 API 字段值",
  "lines": [],
  "state": "truncated",
  "returned": 5000,
  "truncated": true,
  "error_code": ""
}
~~~

state 枚举：

| 状态 | 含义 | 页面行为 |
| --- | --- | --- |
| disabled | call_log 未启用 | 显示配置入口说明，不请求导出 |
| empty | 已启用但尚无持久化记录 | 显示空状态和手动刷新 |
| ready | 读取成功且未截断 | 显示内容和行数 |
| truncated | 达到行数或字节上限 | 显示内容、返回行数和截断说明 |
| partial | 尾读成功但最新缓冲批次 flush 失败 | 显示已持久化内容，并说明结果可能不含最新批次 |
| unavailable | 数据路径不可用、文件打开或读取失败 | 清除旧结果，显示错误码和重试按钮 |
| invalid_request | tail 参数无效或为负数 | 显示请求参数错误，不展示旧结果 |

error_code 使用稳定的小写标识：path_unavailable、read_failed、flush_failed、invalid_tail。浏览器只显示对应的安全提示文案，不显示系统异常文本。

读取失败的内部异常只写入服务端日志，不把堆栈或系统错误细节发给浏览器。绝对路径字段 path 暂时保留其当前响应语义以兼容现有客户端；新 UI 不展示该字段。已登录的 Dashboard 用户仍可从接口响应中看到该字段，是否在后续接口中移除需先确认仓库外客户端依赖。

### 5.3 写入与读到最新记录

当前 API 会先调用 _flush_call_log 再读取文件。保留该顺序。为区分“读文件失败”和“尚无记录”，日志分支应获得 flush 的可观察结果；若 flush 失败，状态至少提示结果可能不含最新批次，不得把旧文件内容标为完整最新结果。

若日志数据路径为空，返回 unavailable；若文件不存在但路径可用且 call_log 已启用，返回 empty。flush 失败时返回 partial，并保留文件中已读到的完整行，但不能宣称这些行包含最新调用。

现有 flush 失败时的内存缓冲和部分写入语义需要在实现阶段单独检查。不要在没有测试的情况下将失败批次简单重复追加，以免出现重复日志行。

> **Why & What：显式日志状态**
>
> **What：**在日志响应中增加 state、returned、truncated 和 error_code 字段。
>
> **Why：**当前读取失败会返回空行，与尚无记录无法区分；新增字段不改变统计摘要响应，也不表示 provider 调用成功。
>
> **替代方案：**由前端仅检查 lines 是否为空，改动更少，但不能区分禁用、空文件和读取错误。
>
> **回退：**旧版前端可继续使用 enabled、path 和 lines；新界面遇到缺少 state 的响应时按旧契约降级呈现。

## 6. UI/UX 设计

### 6.1 状态展示

日志面板状态由单一状态机驱动：

- **加载中**：显示“正在读取”，禁用重复刷新；保留旧内容时标明其为上一次结果。
- **未启用**：说明需在插件配置中启用 call_log，并明确该设置默认关闭。
- **暂无记录**：说明尚未产生或落盘调用记录，可手动重试。
- **读取成功**：显示“显示 N 条”，有截断时明确显示“仅显示最近 N 条”或“受读取上限限制”。
- **部分结果**：显示已持久化行，并说明最近一批可能尚未写入。
- **读取失败**：清除旧结果，显示通用原因和重试按钮；不显示服务器路径。
- **请求过期**：当用户切换条数或刷新后旧请求晚到，丢弃旧响应，不改当前选择和内容。

成功/失败/加载状态通过 aria-live="polite" 状态区播报。刷新按钮文本保持稳定，加载时设置 disabled 并在完成后恢复。无记录或失败时禁用导出。

### 6.2 隐私与导出

日志包含会话标识。日志面板在首次打开时显示简短提示：“调用日志含会话标识，导出文件请妥善保管。”导出按钮可用时仍允许用户直接下载，不增加不可关闭的确认弹窗；点击导出后在 live region 确认导出的行数。新 UI 不展示绝对数据目录路径。

### 6.3 可访问性与窄屏

- 状态文字与颜色同时表达结果，不依赖红绿区分。
- 刷新、读取条数和导出按钮使用可见焦点样式及明确标签。
- 读取条数按钮继续同步 aria-pressed。
- 日志内容保留等宽字体和横向滚动，窄屏不挤压操作按钮。
- 成功结果更新时避免无意移动焦点；失败后焦点保留在触发刷新的按钮。

## 7. 并发和失败语义

- 日志请求使用单调递增 request generation；仅当前 generation 可以更新页面。
- 用户切换读取条数后，旧请求结果丢弃；不取消不支持取消的 bridge 请求。
- 缺少日志文件且 call_log 已开启时返回 empty；读取权限或 I/O 错误返回 unavailable。
- JSON 响应格式错误或缺少 lines 时，不复用上次的数据冒充新结果。
- 单次读大小严格受行数与字节数双重上限约束。
- 服务端保留当前 API 的 enabled、path、lines 字段，新增 state 等字段为加法扩展。

## 9. 取舍、成本与风险

> **Why & What：有界尾读而非全量分页**
>
> **What：**保留 tail 查询方式，以固定最大行数和读取字节数限制单次工作量。
>
> **Why：**当前页面只需要最近记录，用户已通过 200、1000 和“全部”选择读取量。有界尾读能沿用接口和交互，只需把“全部”改成受限的最近记录。
>
> **替代方案：**分页支持浏览任意历史，但需要游标、文件变化策略和更多接口状态，成本更高，暂不纳入本轮。
>
> **回退：**若按字节截断造成实现复杂，可先保留 5000 行上限，并拒绝超过字节上限的单条记录，不能退回全文件 read。

上限减少内存和返回体积，但会限制一次导出可取得的历史范围。用户要完整归档时，应在宿主机上复制 calls.log，而不是放宽 Web API 到无界读取。详细状态和竞态保护会增加前端分支，需要以测试而非截图单独覆盖。

## 10. 待确认问题

1. 5000 行与 8 MiB 是否适合作为首版固定上限？建议在本机调用日志行长和 1000 条渲染耗时验证后定值。
2. API 现有 path 字段是否存在仓库外消费者？实施前需搜索仓库调用点，并决定保留空字符串、保留原值但不展示，或走单独弃用。
3. flush 失败时，待写缓冲如何处理？需要测试确认失败写入可能产生部分追加；不应未经验证重试整批记录。
