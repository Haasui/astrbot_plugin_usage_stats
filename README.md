# 用量统计 · astrbot_plugin_usage_stats

按插件和模型归因 token 用量：哪个插件花了多少、用的什么模型。

默认关闭。上机清单见 [`docs/VERIFY.md`](docs/VERIFY.md)——分「已经有证据的」和「还没验的」两段。
记账主路径已在真机上跑过（补丁、归因、用量口径有截图作证）；**视图是后加的，真机一条没跑过**。

## 为什么需要它

AstrBot 自带的用量统计只覆盖**主对话**那一次调用。装了十几个插件之后，好几个会在背后自己调模型（判断要不要接话、抽取记忆、判定图片……）。这些调用记在账单上，却看不出是谁花的。

## 为什么必须越界

已核实 `astrbot/core/star/context.py:208`：

```python
llm_resp = await prov.text_chat(...)   # 直调 provider，不经过 filter 流水线
```

官方钩子 `on_llm_request` 只覆盖主对话。不包一层 provider，就永远看不到插件那一半。

越界的三条自律：**只读不改 / 默认关闭 / 卸载严格还原**。记账自己的故障一律吞掉，绝不影响对话。

## 分层

| 文件 | 层 | 职责 | 依赖 AstrBot |
| :--- | :--- | :--- | :---: |
| `attribute.py` | 归因 | 从调用栈模块名挑出插件名 | 否（纯逻辑） |
| `stats.py` | 统计 | 用量累加、模型聚合、天 × 模型折叠 | 否（纯逻辑） |
| `store.py` | 落盘 | 序列化、合并、滚动清理 | 否（纯标准库） |
| `patch.py` | 越界 | 类级补丁与精确还原 | 否（目标类由装配层传入） |
| `main.py` | 装配 | 装补丁、记账、落盘、指令 | 是 |

## 指令

| 指令 | 说明 |
| :--- | :--- |
| `/usage`（别名 `用量` `usg`） | **一行一个模型**：调用数、token、缓存命中。跨插件按模型聚合 |
| `/usage full` | 明细：按插件拆到模型，带失败数与图片数 |
| `/usage day` | 同 `/usage`，只看今天 |
| `/usage week` | 同 `/usage`，看近 7 天 |
| `/usage status` | 运行期状态：补丁数、本次运行记录数、未落盘条数、保存失败次数 |
| `/usage help` | 子命令清单 |
| `/usage_clear` | 清空**本次运行**的内存记录，落盘历史不动 |
| `/usage_reset` | 清空**落盘的历史**（连同内存）。改了归因规则、旧数据不可信时用它 |

**`/usage` 和 `/usage status` 是两种口径，不要拿它们对数。** `/usage` 的数字是「落盘历史 + 本次」，
而 `/usage status` 里的「本次运行记录」只算这次启动以来。两者不相等是正常的。

**为什么默认按模型聚合而不是按插件**：同一个模型在不同插件下单价相同，所以用量和命中率可比；
跨**模型**比 token 占比没有意义——同一个 token 在 R1-8B 和 V4-Flash 上差价几十倍。
要看「哪个插件花了多少」用 `/usage full`。

开 `debug` 后，每笔调用会多出一行日志（插件、模型、调用方式、会话、图片数）——`/usage` 只给一屏摘要，明细在这里看。

## 🖥 WebUI 视图

排行表右上角可以切「按插件 / 按模型」：

- **按插件**（默认）：父行是插件，点开是它用的模型
- **按模型**：父行是模型，点开是用它的各个插件 —— 这一档才回答得了「某个模型到底被谁在用」

子行的占比分母跟着变：按插件时是全局，**按模型时是这一行模型自己的总量**。后者才有意义，
因为同一个模型在不同插件下单价相同；跨模型比 token 占比说明不了花销。

**图表的堆叠口径不跟着切**（接口只有「按插件按天」的序列）。切到按模型时表头旁会写明
「图表仍按插件堆叠」，免得以为图和表对不上。

页面最下面是**调用日志**面板：开了 `call_log` 就能在这里直接看最近 50/200 行，
按 `in` 降序——想先看的是「哪几笔最肥」，不是时间顺序。没开就显示提示，不用去容器里翻文件。

插件页里有一个「用量统计」视图。顶部是状态与时间范围，下面两块：按天的柱状图，和插件 → 模型的排行表。

| 区域 | 内容 |
| :--- | :--- |
| 顶部 | 状态点（补丁几处、本次运行记录几次）、时间范围、刷新 |
| 概览 | 四张卡片：范围合计、调用次数、失败、缓存命中。每张带一句与上一同长假期的对比 |
| 每日用量 | 按天堆叠，一种颜色一个插件，下方有图例，带四等分参考线。悬停或聚焦出当天前三名的构成 |
| 排行 | 插件 → 模型两级。表头可点排序，点插件名收起模型明细（刷新后仍保持）；每一行都有「趋势」，把图切成那一个插件或那一个模型，图表面板标题旁会出现「取消下钻」 |

每 30 秒自己刷一次，也可以手动刷新。

### 文件结构

```
views/usage/index.html   骨架，没有内联样式和脚本
views/usage/style.css    设计系统
views/usage/app.js       取数与渲染
```

`index.html` 只引用同目录的 `./style.css` 和 `./app.js`。

### 设计系统

`style.css` 开头写了规则：主色取 Dashboard 的蓝，中性色偏冷，图表和占比条共用主色，不引外部字体与图标库。颜色全走 CSS 变量，分亮暗两套。

明暗模式的优先级：宿主经 bridge 告知的 `isDark` > 宿主自己设的 `data-theme` > 系统偏好。图标一律内联 SVG（`currentColor` 配 `stroke-width: 2`），不依赖图标字体。

骨架屏的流动动画在 `prefers-reduced-motion: reduce` 下会停掉。持续动效对前庭敏感的人不友好，这类守卫容易漏。

图表用的是 roving tabindex：**整张图只占一个 Tab 停留点**，方向键在柱子之间移动，Home / End 跳到首尾。
每根柱子都是按钮的话，30 天就是 30 个停留点——键盘用户想走到下面的表格得先按 30 次 Tab。

选中的时间范围会记在本机，下次打开还是那个范围。取数失败会重试两次（只重试 GET，它幂等）。

首屏数据还没回来时铺一层骨架（灰条 + 灰块），而不是留两块空白面板。**骨架只在首屏出现**——自动刷新时保留旧数据，否则每 30 秒闪一次。

环比只在选了具体范围时出现（「全部」没有上一周期可比）。上一周期是 0 时写「新增」，不给百分比；相差不到 0.5% 写「持平」。缓存命中比的是百分点差，不是命中量差——比率和计数不是一回事。点「趋势」只看单个插件时也不显示环比，因为接口不返回单插件的历史。

### 取数

数据来自 `/{插件名}/stats?days=N`，与 `/usage` 指令同源。桥接用官方的 `window.AstrBotPluginPage`，SDK 由 `/api/plugin/page/bridge-sdk.js` 提供。图表是纯 div，没有图表库。

下钻到模型时要多带两个参数（`&plugin=X&model=Y`），服务端才现算那一条日序列。**模型级序列不常驻在响应里**——视图每 30 秒轮询一次，让每次轮询都背一份全量的模型级数据不划算。

## 配置

`_conf_schema.json` 里的六项。全都有默认值，装完不改也能跑。

| 键 | 默认 | 作用 |
| :--- | :--- | :--- |
| `enabled` | `false` | 总开关。**关着的时候一处补丁都不装** |
| `memory_cap` | `20000` | 内存里最多留多少条。超了先落盘再丢最旧的。设 0 不限制 |
| `keep_days` | `60` | 落盘保留多少天，更旧的在保存时丢掉。设 0 不清理 |
| `save_every` | `50` | 每多少条落一次盘。设 0 表示不按条数存 |
| `refresh_interval` | `60` | 隔多少秒重扫一次 provider 子类。设 0 关闭 |
| `call_log` | `false` | 写独立的 `calls.log`：一行一笔，带请求构成和耗时。只记长度，不记正文 |
| `call_log_lines` | `20000` | 调用日志保留多少行。攒到两倍才裁，避免每次追加都重写整个文件 |
| `debug` | `false` | 每笔调用输出一行日志，含会话。`/usage` 里不显示会话 |

**保存不只看 `save_every`**：收到 `/usage`、插件卸载、以及内存超限时都会落盘。所以 `save_every=0` 不等于「只在卸载时保存」。

**`refresh_interval` 为什么必须存在**：AstrBot 的 provider 子类是按需导入的。插件初始化跑在它们被导入之前时，`Provider.__subclasses__()` 是空的，一处都挂不上；而挂不上就收不到调用，也就没有任何事件能触发重扫。所以重扫只能是时间驱动的。

**改了归因规则之后**，旧数据里存的是**当时记下的插件名**，不会回溯修正。这时用 `/usage_reset` 清掉重来。
